# HUSHFALL: the developer key (a code map for engineers who did not build it)

PT-066 (M13 of the commercial plan). This is a map, not a manual: where things live, what flows where, the rules that keep it honest, and how to add the usual things. The facts that change daily (status, what is built, what is unplayed) are in `PRODUCTION_LOG.md`; the rules an agent must obey are in `AGENTS.md`; the design is in `design/`. If this file and the code disagree, the code is right and this file is a bug.

## 1. The shape in one page

An original desktop-browser first-person shooter. A **fixed-step, deterministic, DOM-free simulation** (`src/engine`) is the truth. A **Three.js view** (`src/render`) draws what the simulation says; a **WebAudio synth** (`src/audio`) sounds what it says; a **DOM shell** (`src/game`) owns the page, the input devices, the menus and the clock. Content is **data**: 68 map files (`maps/*.json`) compiled from JavaScript sources (`maps-src/*.level.mjs`) by a small kit (`tools/mapkit`). Every picture is **baked** offline from p5.js (+ p5.brush) recipes (`tools/baker`) into `assets/baked/*.png`; every sound is **synthesised** at run time (`src/audio/synth.js`). Nothing is downloaded, scanned or generated by a service.

```
keyboard / mouse / pad --> InputState (engine/input.js) --> cmd (one per tick)
                                                              |
              +-----------------------------------------------v---------------+
              |  step(world, cmd)  (engine/world.js)  fixed 60 Hz, seeded RNG  |
              |  state is plain data; effects are EVENTS in w.events           |
              +-----------------------+-------------------+--------------------+
                                      | drainEvents(w)    | w (read only)
                 +--------------------v--+   +------------v-----------+   +---------------------+
                 | GameView (render/)     |   | AudioEngine (audio/)   |   | UI + HUD (game/)    |
                 | meshes, decals, post   |   | events.js -> synth.js  |   | DOM, journal, menus |
                 +------------------------+   +------------------------+   +---------------------+
```

**The three rules everything else follows.** (1) The simulation never reads a view, a clock or a device; the wall clock only decides how many fixed ticks to run (`engine/loop.js`). (2) Render, audio and UI only READ the world and DRAIN its events; they never write it (the story scenes and the replay are built on that: a scene is the view with a different camera while no tick runs). (3) A feature the simulation does not use is absent from the state: fields are created lazily by the code that needs them (`p.loads`, `e.snipeT`, `w.tears`...), so a world that never meets a feature is byte-for-byte what it was, and `tools/dev/route-fingerprint.mjs check` proves it.

## 3. The tick, the events, the views

`createWorld(map, { seed, difficulty, carry, choices })` returns plain data. `step(w, cmd)` advances 1/60 s: player movement and weapons, enemies (`updateEnemy` and its per-creature hooks), projectiles, doors and moving floors (`script.js`), clocks (`hive.js`, `breath.js`, `tide.js`... pure functions of `w.time`), triggers. Anything the outside world should hear or see becomes an event pushed on `w.events` (`emit(w, type, data)`); `drainEvents(w)` hands them over once. `hashWorld(w)` is the determinism check used by the tests and the browser-versus-node parity check.

The view builds once per level (`new GameView(renderer, textures, map, world)`) and each frame calls `render(w, alpha, dt)`: it interpolates the previous and current sim state, poses creature rigs, updates the lights, decals and effects, and writes the post-pass uniforms. `handleEvents(ev)` turns events into debris, decals, shakes and flashes. A cinematic sets `view.setCinematic(pose)`; the eye is the scene's, the weapon scene is not drawn, and the simulation is simply not stepped.

## 4. Content pipeline

**A map** is an ASCII grid plus layers (heights, ceilings, floor effects) and an entity list (player, exits, enemies, pickups, switches, doors, props), triggers, messages, an intro and an outro. A source `maps-src/<ID>.level.mjs` builds it with the `Level` builder; `node tools/mapkit/compile.mjs <ID>` validates and writes `maps/<ID>.json` (a dry run: `MAP_OUT=<dir>`). Order inside a source matters: objects, then shaping (`S.hall`, `S.chamfer`), the encounter and roster blocks, `L.layers()`, then the compile steps (drops, squeeze). `npm run map -- <ID>` is the per-map loop (compile, plan image, verify, validate, one verdict line); `npm run map:new -- <ID>` scaffolds a new one.

**Status is derived, never typed.** PLANNED, IMPLEMENTED (loads), AGENT_VERIFIED (automated pass plus a canonical route that reaches the exit), COMPLETE (a recorded human review: agents may not award it). `npm run validate` computes it from `validation/maps/<ID>.json`; evidence goes stale when the map, its routes or any source set it depends on changes (`tools/textsha.mjs`).

**The gates** (`npm run verify-map -- <ID>`, `src/engine/viability.js`): every route completes on three difficulties; a passive runner must not get through; a perfect bot must take damage and finish on enough seeds (either fighter policy counts: a standing one, then a strafing one); a gate-skip probe; ammunition slack; a robustness run (aim error, fewer pickups); placement (no trap cell, findable gate objects); and the real-game evidence from headless Chrome. `tune-roster.mjs`, `try-enc.mjs` and `tune-add.mjs` try a change against the gates in a scratch folder.

**Art.** `node tools/bake.mjs <asset id>` bakes one recipe (`BAKE_PREVIEW=<dir>` writes elsewhere); `refresh-manifest.mjs` rebuilds the asset manifest. Creature atlases are `choir_<kind>.png` from `recipes_choir.js` with the cells declared in `src/render/choir_cells.js`. p5.brush rules (one page per bake, no brush fills in a transparent canvas, plain p5 for hard shapes) are in `ART_BIBLE.md`.

**Text** is held to `design/LORE.md` section 5; `tools/dev/prose-lint.mjs` is that section as code and `tests/` hold the mechanical part.

## 5. Recipes

**Add a creature.** A row in `ENEMIES` (`defs.js`: hp, speed, `height`, `hitRadius`, attack, any ability block); the behaviour as a pure module hooked in `updateEnemy` (see `marksman.js`); a rig in `models_choir.js` or `models_hive.js` registered in `FACTORIES`; atlas cells in `choir_cells.js` and a recipe in `recipes_choir.js`, then bake and `refresh-manifest.mjs`; sounds in `synth.js` and event mappings in `audio/events.js`; a bestiary line (`game/bestiary.js`); a Range target; add it to `GUARDED` in `tests/silhouettes.test.js`. Then `node tools/look/check-rigs.mjs <kind>` and `node tools/dev/measure-rig.mjs <kind>` fit the hit volume to the drawn body. The audio, rig, hit-volume, grounding and Range tests enumerate every kind and fail until each has its part.

**Add a mechanic.** A pure module under `src/engine`, called from a hook in `world.js`; state lazy; events for anything seen or heard; a map key validated in `mapformat.js`; a view in `src/render` that reads the sim; a test that proves a world without the feature is unchanged (`route-fingerprint.mjs save` before, `check` after).

**Add a pickup.** A row in `PICKUPS` (`defs.js`) and, for a new `type`, a branch in the pickup loop of `world.js` (see `crate.js` for a pure one); a name and a tier in `src/game/toasts.js`, a line in `src/game/itemhelp.js`, a model in `pickupMaker` (`view.js`); the tests that enumerate every kind (`pickup-cards`, the item help) fail until each has its part. A map placing it appends it to `MAP.entities` AFTER every other entity (no id shifts).

**Add a map action.** The key in `ACTION_KEYS` and its validation (`mapformat.js`), its effect in `runAction` (`script.js`).

**Add a weapon.** `WEAPONS` and `PICKUPS` in `defs.js`, the key slot in `SLOT_KEYS`, a rig under `src/render/models_*.js` and a stance in `weapon-pose.js`, the firing code in `world.js` (`fireWeapon`), sounds, an entry in `game/itemhelp.js`, the Range, tests; then place it with `place-near.mjs` and re-run the gates of the maps it touches.

## 6. How to know it works (the two halves)

SIM TRUTH: `npm test` (the node suite, headless, about 1,050 tests; `tests/maps.test.js` plays the gates of every shipped map when it loads and takes the better part of half an hour, so run the rest without it while iterating: `node --test $(ls tests/*.test.js | grep -v maps.test)`), the route fingerprints, the bots. RENDER TRUTH: `tests/frame-loop.test.js` runs the real frame loop (`beforeStep`, `step`, `handleEvents`, `audio.update`, `render`, `ui.hud`) headless over every map against stand-ins (a throw there is a black screen for a player: run it after ANY change under `src/render`, `src/game` or `src/audio`), and the headless-Chrome jobs (`npm run browsercheck`, `browser-maps`, `render-ground`, the shoot and probe tools) draw and measure what a GPU actually does. Neither replaces the other. **A headless browser's suspended AudioContext hides audio crashes**; the node frame-loop test uses a "running" one for that reason.

## 7. Gotchas that cost real time

- **A trailing `// comment` on a one-line statement swallows whatever follows it on that line.** It broke a bot, the weapon-fire line (no shot woke anyone) and a capture tool; `tests/fire-noise.test.js` guards the worst one. Put the comment at the END of the line.
- Chrome jobs: never edit `src/` or `maps/` while a Vite-served page is running (HMR reloads it mid-job); launchers refuse the pointer lock (`Element.prototype.requestPointerLock` replaced before any page script) and `src/game/lockpolicy.js` refuses it for any driven browser; run jobs at idle priority on two cores (`tools/dev/low.ps1`).
- Evidence is stale after ANY change in `src/engine`, `src/render`, `src/game`, `src/audio` or `assets/baked`: make the changes first and regenerate once.
- A map source must put material-swap blocks BEFORE `L.layers()` is read, and a `MAP.squeeze` is applied last, so cells in a test for a squeezed map are authoring cells (`cellToShipped`).
- Bot gates are chaotic near their edges: a one-creature or one-pickup change can flip a hard seed (the arc lamp at one lane cell failed the strafing robustness run and at two others passed). Always re-run `verify-map` after the LAST compile.
- ENTITY IDS HAVE A PARITY EFFECT: a creature takes its steering side when blocked from `e.id % 2` (`world.js`), and a creature a map SPAWNS gets its id from the shared counter, so ONE new entity (a pickup counts) in a map that spawns flips the parity of everything spawned later and can move a main route (found on C2M18, three Normal runs). Add entities in pairs, or run `route-fingerprint.mjs check` before trusting it.
- Windows: the repo files are CRLF; edit with a tool that preserves line endings, and do not write regexes or backslashes through a shell string.

## 8. Releasing

`npm run verify` (validate + test + build), `npm run check-dist` (the build folder uploads as it stands), `npm run licences` (`THIRD_PARTY_NOTICES.md`; three.js is the only code that ships), `npm run browsercheck` and `node tools/dev/browser-map.mjs --all` for the real-game evidence, `npm run audio-qa` (203 sounds), the performance probes in `tools/dev/probe-*.mjs`, `design/PERFORMANCE_PLAN.md` for the minimum spec. `design/COMMERCIAL_AND_USAGE_PLAN.md` workstream M lists what a store release still needs from the owner (name search, the licence holder, store assets, outside testers).
